# 阶段 0：工程基线闭环实施清单

## 1. 目标

在不扩展业务功能的前提下，先把平台的工程底座补齐，使后续 AI、支付、恢复、社区等功能都能在统一规范下落地。

本阶段的核心目标：

- 统一权限校验
- 统一状态流转
- 统一审计事件
- 统一错误码
- 统一失败恢复策略
- 统一 tenant isolation

---

## 2. 实施原则

1. 先统一底座，再扩展业务
2. 所有写操作必须有 tenant scope
3. 所有关键动作必须有 audit event
4. 失败必须保留错误码、上下文和重试入口
5. 不允许“静默成功”“静默失败”

---

## 3. 任务拆解

### 3.1 权限与租户隔离

#### 目标
避免跨租户越权、跨商家读取、跨角色访问。

#### 任务
- 明确所有 API 的认证主体：buyer / merchant / employee / admin / consumer
- 明确引入统一 tenant scope 中间件
- 为所有写接口强制校验 merchantId / buyerId / adminId
- 对商家员工使用最小权限模型
- 对 AI employee 的可执行工具做权限包装

#### 产出物
- 权限矩阵文档
- 通用 auth guard 说明
- 公共 request context schema

#### 验收标准
- 跨租户读取失败
- 非授权角色不能发起变更
- 审计日志能追踪操作人和所属租户

---

### 3.2 状态机统一

#### 目标
所有关键业务统一走同一套状态流转，避免状态混乱导致闭环断裂。

#### 推荐状态集

- draft
- pending
- approved
- rejected
- active
- paused
- archived
- failed
- retry

#### 使用范围
- AI employee request
- product content draft
- creative draft
- sales quote draft
- merchant support conversation
- backup / recovery job
- payment transaction

#### 产出物
- 通用状态定义文件
- 每个模块状态流转图

#### 验收标准
- 每个关键动作都有明确状态转换
- 任何从 active/approved 到 failed 的操作都须保留原因
- 状态转移必须可追踪

---

### 3.3 审计事件规范

#### 目标
所有关键行为都可追溯，确保生产环境能回答：谁做了什么、什么时候做的、结果是什么。

#### 关键审计字段
- action
- actorId
- actorRole
- merchantId
- adminId
- targetType
- targetId
- beforeState
- afterState
- ip
- userAgent
- createdAt
- result
- errorCode
- errorMessage

#### 建议审计事件类型
- auth.login
- auth.logout
- merchant.create
- merchant.update
- product.create
- product.publish
- ai.employee.request
- ai.employee.approve
- ai.employee.reject
- ai.task.run
- ai.task.approve
- payment.created
- payment.refunded
- backup.created
- recovery.drill.started
- recovery.drill.completed

#### 产出物
- audit event schema
- audit event sample payload
- 关键 API 审计点清单

#### 验收标准
- 每个关键写操作都记录
- 审计事件不可覆盖
- 审计记录保留失败上下文

---

### 3.4 统一错误码与异常处理

#### 目标
让系统能区分“业务错误”和“基础设施错误”，提高排障效率。

#### 错误分类
- validation
- auth
- forbidden
- rate_limit
- not_found
- conflict
- provider_failure
- infra_failure
- retryable_error
- idempotency_error

#### 标准返回格式
```json
{
  "success": false,
  "error": {
    "code": "FORBIDDEN",
    "message": "You do not have permission to perform this action.",
    "requestId": "req_123",
    "retryable": false
  }
}
```

#### 产出物
- 错误码表
- 公共 API error helper
- 错误日志策略

#### 验收标准
- 业务错误和系统错误分离
- 失败必须保留 requestId
- 重试字段明确

---

### 3.5 幂等与重试能力

#### 目标
避免重复点击、重复回调、重复 webhook 导致重复写入。

#### 要求
- 所有支付、导入、AI 生成、备份任务均实现幂等 key
- 同样任务重复提交应返回已存在结果而不是重复创建
- webhook 重放必须被识别并跳过重复执行

#### 产出物
- idempotency key 规范
- 关键任务唯一键定义
- 重试策略说明

#### 验收标准
- 重复请求不会产生重复副作用
- 回调重放不会重复写库

---

### 3.6 恢复与回滚机制

#### 目标
系统不能只会“失败”，必须知道“如何恢复”。

#### 必须覆盖
- 写事务失败时的回滚
- AI 生成失败的重试
- 文件上传失败的清理
- 支付 webhook 失败的补偿
- 数据恢复 drill 的回放机制

#### 产出物
- 恢复策略文档
- 关键流中的补偿步骤说明

#### 验收标准
- 每个关键流程都有失败恢复方案
- 关键失败都有重试或人工兜底

---

## 4. 实施顺序

1. 先统一权限和 tenant isolate
2. 再统一状态机和审计
3. 再统一错误码和恢复策略
4. 再补 AI / 支付 / 恢复等业务闭环

---

## 5. 当前项目执行建议

优先在现有项目中补以下内容：

- 通用认证/授权 guard
- audit event helper
- 通用状态 enum
- 统一错误 response
- 关键业务操作的幂等 key

不建议先做 UI 扩展，不建议继续堆页面功能，先把底座修好。

---

## 6. 第一个实际交付目标

在阶段 0 完成后，要求至少满足：

- 所有核心写操作都能写审计
- 所有核心读取都过滤租户
- 所有关键状态都能追踪
- 所有失败都有 error code 和 retry hint
- 所有高风险动作都有明确权限和审批

这将为后续 AI、支付、灾备等阶段打下落地基础。

## 7. Runtime Integration 进度

首批运行时接线已完成，尚不代表所有写 API 均已覆盖：

- `POST /api/company/products`：租户 ID 仅以已认证 company token 为依据，校验所选 merchant 归属；商品创建与审计记录在同一事务中提交。
- `PATCH /api/admin/ai-employee-requests/:id`：只允许 `requested -> active/declined`，通过条件更新防并发重复审批，并与审计记录原子提交。
- Express 为请求分配 `X-Request-Id`；内部异常通过统一错误边界返回安全错误码和消息，内部详情仅进入服务端日志。
- 审计表增加 requestId、merchantId、状态、结果、错误码和脱敏 metadata 字段。

部署前必须执行新增 Prisma migration。剩余写路由仍需按权限矩阵分批接入 tenant guard、状态约束与事务审计；在完成路由盘点和逐项验收前，不得将 Phase 0.1 标记为全量完成。
