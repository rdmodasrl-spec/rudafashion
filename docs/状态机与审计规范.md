# 状态机与审计规范

## 1. 背景

为了让 RUDA 平台具备真正的工程闭环，所有重要业务对象都必须使用统一状态机和审计事件流。

本规范适用范围：

- 商品
- 订单
- AI employee request
- AI task / draft
- creative draft
- merchant support conversation
- payment transaction
- backup / recovery jobs

---

## 2. 通用状态机

### 2.1 基础状态集

```text
draft -> pending -> approved -> active
        \-> rejected
        \-> failed -> retry -> pending
active -> paused
active -> archived
active -> failed
failed -> retry
```

### 2.2 状态定义

- draft: 初始草稿，未提交
- pending: 等待审批、等待执行、等待回执
- approved: 已审核通过
- rejected: 审核不通过
- active: 正常生效
- paused: 暂停，不再执行
- archived: 归档，不再属于主流程
- failed: 执行失败，保留具体原因
- retry: 重试状态，等待重新执行

---

## 3. 关键流程状态设计

### 3.1 AI employee request

```text
draft -> pending -> approved -> active
                    \-> rejected
                    \-> paused
```

说明：
- 申请创建/开通 AI 员工时，必须经过审批
- 审批后才绑定权限
- 可由 merchant 暂停

### 3.2 AI task / workflow

```text
draft -> pending -> running -> succeeded
                  \-> failed -> retry -> pending
```

说明：
- 所有 AI 调用必须持久化任务状态
- 失败后必须保留失败原因和重试动作

### 3.3 Creative draft

```text
draft -> pending_review -> approved -> attached
                     \-> rejected -> cleared
                     \-> failed -> retry
```

说明：
- 生成后必须进入 review flow
- 审批前不允许写入业务对象
- rejected 必须清理私有资源

### 3.4 Payment transaction

```text
pending -> authorized -> confirmed
   \-> failed
   \-> cancelled
confirmed -> refunded
```

说明：
- 付款类状态必须支持 webhook 和幂等处理
- 需要保留交易证据

### 3.5 Backup / recovery job

```text
pending -> running -> succeeded
                \-> failed
succeeded -> archived
```

说明：
- 备份任务和恢复 drill 必须保存执行上下文
- 恢复流程必须保留 result artifact

---

## 4. 审计事件规范

### 4.1 标准字段

每个审计事件必须包含：

- eventName
- actorId
- actorRole
- merchantId
- adminId
- targetType
- targetId
- beforeState
- afterState
- result
- errorCode
- errorMessage
- ip
- userAgent
- createdAt

### 4.2 审计事件示例

```json
{
  "eventName": "ai.employee.approve",
  "actorId": "admin_001",
  "actorRole": "admin",
  "merchantId": "merchant_123",
  "adminId": "admin_001",
  "targetType": "ai_employee_installation",
  "targetId": "install_456",
  "beforeState": "pending",
  "afterState": "active",
  "result": "success",
  "errorCode": null,
  "errorMessage": null,
  "createdAt": "2026-10-02T10:00:00Z"
}
```

### 4.3 审计不允许缺失的场景

- 登录/登出
- 角色授权/撤销
- 商品创建、修改、发布、归档
- AI 工具执行
- AI 审批或拒绝
- 支付成功/失败/退款
- 备份与恢复执行
- 关键 settings 变更

---

## 5. 审计输出要求

### 5.1 必须保留
- 事件时间
- 执行人
- 目标对象
- 前后状态
- 结果和失败原因

### 5.2 禁止
- 不记录失败的关键动作
- 不记录 actorId
- 不记录 targetId
- 不保留错误上下文

---

## 6. 工程要求

### 6.1 统一名称规范
- event names 全部小写并使用点语法
- 必须避免同义词混用
- 如统一使用 `ai.employee.approve`，不要混用 `approve_ai_employee`

### 6.2 统一日志级别
- info: 正常业务动作
- warn: 条件性、边界、可恢复问题
- error: 失败、异常、拒绝
- critical: 影响业务可用性的故障

### 6.3 统一回写策略
- 成功写入返回 result success
- 失败返回 error code + retryable flag
- 失败后必须仍然保留审计记录

---

## 7. 实施检查清单

- [ ] 所有关键对象都定义状态
- [ ] 每个关键动作都有审计事件
- [ ] 失败动作必须保留原因
- [ ] 关键状态转换必须可回溯
- [ ] 审计字段统一一致
- [ ] API 结果统一返回 error code

---

## 8. 结论

如果没有统一状态机和审计规范，系统可能看起来功能很多，但一旦发生：

- 支付失败
- AI 任务异常
- 恢复处理异常
- 权限越权
- 数据不一致

都无法快速定位和修复。

因此，工程基线阶段必须先完成状态机和审计规范，再推进任何业务扩展。
