# RUDA Fashion 工程级系统闭环补全路线图

## 1. 目标

本路线图的目标不是继续堆功能，而是把“已存在的功能”补成真正的工程级闭环：

- 可执行
- 可审计
- 可回溯
- 可恢复
- 可验证
- 可上线

最终实现的标准不是“页面能点”，而是“业务动作完成后，权限、数据、状态、审计、恢复和监控都能闭合”。

---

## 2. 闭环判定标准

一个功能是否算“闭环”，至少满足以下 6 条：

1. 有明确发起入口
2. 有权限校验
3. 有状态流转
4. 有数据落库
5. 有审计记录和错误回写
6. 有失败恢复 / 回滚 / 兜底

如果缺任一条，就属于“半闭环”或“功能骨架”。

---

## 3. 当前项目评估结论

根据当前代码和文档，整个项目可以分为三层：

### 3.1 已比较成熟的闭环层
- 商品管理
- 订单管理
- 商家后台运营
- 平台管理后台
- 前台采购/结账链路
- 公共 SEO 与多语言路由
- 一部分备份脚本与部署机制

### 3.2 明显未闭环的层
- ModaGPT / AI 员工工作流
- AI provider 实际接通和 fallback
- Billing / 支付回调闭环
- 真实灾备恢复演练
- 真实生产环境校验

### 3.3 框架已存在，但仍缺业务落地
- AI 创意生成与审核
- 客服 RAG 与知识库运营
- Fashion Community 迁移与验证
- 批量运营分析与告警链路

---

## 4. 总体实施原则

### 4.1 先做“闭环”，再做“扩展”
不能再继续为了“功能看起来很多”堆页面和接口，必须优先补齐：

- 权限
- 数据一致性
- 状态机
- 审计日志
- 异常处理
- 恢复方案

### 4.2 统一标准状态机
所有关键动作统一采用这样的状态：

- draft
- pending
- approved
- rejected
- active
- archived
- failed
- retry

避免各模块各自发明状态词，导致链路不可追踪。

### 4.3 每个功能必须有“可验证产物”
每个模块都需要具备：

- API contract
- schema / table change
- audit event
- smoke test
- rollback plan

---

## 5. 执行路线：分阶段推进

# 阶段 0：统一工程基线

## 目标
建立统一的基础闭环基座，后续功能都在这个基座上运作。

## 关键任务

### Step 0.1：统一权限与租户模型
- 明确所有 API 使用统一 tenant scope
- 明确所有写操作必须校验 merchantId / adminId / employeeId
- 所有查询必须过滤到当前租户数据
- 所有托管接口都要做最小权限原则

交付物：
- 权限矩阵文档
- 统一授权中间件说明
- 关键 API 的权限清单

验收标准：
- 任意跨租户访问被拒绝
- 审计日志可追踪访问人和访问范围

### Step 0.2：统一状态机和审计事件
- 所有核心模块统一状态枚举
- 所有业务写操作产生 audit record
- 所有失败操作必须保留失败码和失败上下文

交付物：
- 通用状态定义文件
- 审计事件规范
- 错误码规范

验收标准：
- 每个关键动作可追踪
- 失败日志能定位到具体服务和上下文

### Step 0.3：统一错误与恢复策略
- 错误分类：validation / auth / rate-limit / infra / provider / business
- 所有 API 返回统一错误 envelope
- 关键写操作支持 retry / idempotency

交付物：
- 错误码表
- 重试/幂等规范
- 回滚策略说明

验收标准：
- API 错误信息可区分业务与基础设施问题
- 重复请求不产生重复副作用

---

# 阶段 1：AI 系统闭环修补

## 目标
把 AI 员工和 AI 工作流补成真正可运营的系统，而不是“能看得到的 demo”。

## 关键任务

### Step 1.1：补全 provider routing 统一入口
- 统一 AI provider 的 route、fallback、timeout、retry
- 统一 provider health check
- 明确 provider 选择是否可配置
- 统一安全限制：不能在浏览器直接打第三方 API

交付物：
- provider router module
- health check endpoint
- provider failure contract

验收标准：
- 不泄露 key
- provider 失败可捕获且可展示
- fallback 可配置

### Step 1.2：补全 AI 工具权限闭环
- 每个 AI employee 角色必须绑定最小权限
- 每步工具调用前重新校验权限
- 不允许 AI 直接修改库存、订单、用户联系信息
- 所有 AI 任务必须记录 audit event

交付物：
- 权限绑定表
- 工具调用 guard
- AI audit log

验收标准：
- 违规调用被拒绝
- 审计日志能看出谁、何时、做了什么

### Step 1.3：补全生成与审批闭环
- 生成结果默认私有，不能自动发布
- 生成结果可预览、可拒绝、可批准
- 批准后才写回真实业务对象
- 生成失败必须保留失败原因和重试入口

交付物：
- 生成草稿状态流
- 审批页面/API
- 审批回写逻辑

验收标准：
- 生成结果不会直接发布
- 审批后才能真正写入业务对象
- 审批状态可追溯

### Step 1.4：补全 quota / rate-limit / retry
- 每种 provider 设定 quota
- 每个 merchant 设定单日和单次上限
- 失败自动重试，但要做幂等和 dead-letter
- 生成任务必须持久化和可查询

交付物：
- quota config
- task queue schema
- retry policy

验收标准：
- 超限被拒绝而非静默失败
- 重试不重复执行业务动作

### Step 1.5：补全真实 provider 验证
- DeepSeek 接通测试必须在真实环境内执行
- Fal AI 真实调用要验证返回格式和图片下载
- OpenAI / Gemini 需要真实账号与相关模型测试
- 模型选择要受 admin allowlist 管理

交付物：
- provider connectivity report
- provider health dashboard
- 模型白名单配置

验收标准：
- 每个 provider 都有真实测试记录
- 失败时有明确诊断信息

---

# 阶段 2：支付与交易闭环

## 目标
把“支付页面可点”升级成“真实交易闭环”。

## 关键任务

### Step 2.1：统一支付状态机
状态必须覆盖：

- pending
- authorized
- confirmed
- failed
- refunded
- cancelled
- disputed

### Step 2.2：补全 webhook 回调链路
- webhook 验证签名
- 防重放
- 幂等处理
- 订单状态同步
- 失败告警

### Step 2.3：补全退款和对账
- 退款状态更新
- 对账结果保存
- 结算记录落库
- 支付失败核查与人工处理

### Step 2.4：补全支付证据和审计
- 每一笔支付必须记录 paymentId、provider、状态、金额、时间
- 支付操作需要 audit log
- 失败/退款必须可追踪

验收标准：
- 付款链路可追踪
- 重复回调不会重复更新订单
- 支付失败能有人处理并记录

---

# 阶段 3：数据恢复与灾备闭环

## 目标
把“备份脚本存在”提升为“生产级恢复可验证”。

## 关键任务

### Step 3.1：补全恢复演练流程
- 创建隔离恢复数据库
- 执行真实备份恢复
- 检查数据完整性
- 验证表和索引
- 验证业务 smoke

### Step 3.2：补全 RPO/RTO 监测
- 记录 last successful backup time
- 记录 backup age
- 记录恢复耗时
- 生成 dashboard

### Step 3.3：补全恢复告警和回放
- restore failure 必须告警
- restore 结果必须保留 artifact
- 失败后保留诊断信息，便于人工排查

验收标准：
- 至少执行一次真实恢复 drill
- 恢复过程可复现
- RPO/RTO 有真实测量数据

---

# 阶段 4：客服与知识库闭环

## 目标
让 AI 客服从“聊天页”升级为“有知识库、有人工接管、有运营闭环”的客服系统。

## 关键任务

### Step 4.1：补全知识库审核链路
- 文章必须经过确认或行业说明分类
- 不允许把未经验证内容当平台事实
- 所有知识库改动都写入审计

### Step 4.2：补全 RAG 数据链路
- 文档 → embedding → retrieval → response
- 检查 retrieval 来源是否可信
- 返回时标记“来源类型”和“置信度”

### Step 4.3：补全人工接管闭环
- AI 不能直接结束高风险问题
- 高风险/不确定请求必须转人工
- 转人工必须保留 reason 和 context
- 人工处理结果必须可存档

### Step 4.4：补全 feedback 与知识库回流
- 用户反馈要能记录
- 反馈可用于知识库修订
- 但不能直接导致 AI 自身知识未经审核更新

验收标准：
- 高风险场景必须转人工
- 反馈能进入 review 流程
- 知识维护仍然由人工审核控制

---

# 阶段 5：Fashion Community 与内容扩展闭环

## 目标
确保社区、媒体和导入流程在真实环境里可迁移、可回滚、可恢复。

## 关键任务

### Step 5.1：Migration Gate
- 先备份
- 再 migration
- 再 count check
- 再 apply
- 再 smoke test

### Step 5.2：媒体存储与 CDN 闭环
- 上传真的写到对象存储
- 删除和回收都符合规范
- 缓存和 CDN 访问路径可验

### Step 5.3：内容审核与 moderation
- 评论、帖子、媒体都要可审核
- 删除和隐藏操作要留痕
- 违规内容支持人工回收

验收标准：
- 社区数据导入有数据比对
- 媒体可访问且可回收
- 删除和审核都有痕迹

---

# 阶段 6：生产上线门禁

## 目标
系统在“上线前”必须完成交付门禁，而不是靠感觉上线。

## 必须完成的门禁清单

### A. 功能门禁
- 每个关键功能都有 API contract
- 每个功能都有 status/state flow
- 每个功能都有失败处理
- 每个功能都有审计记录

### B. 数据门禁
- 关键表有 migration
- 关键写入有回滚方案
- 关键查询有租户过滤
- 关键数据有备份和恢复脚本

### C. 安全门禁
- No secret in frontend / config / logs
- 所有外部调用走后端
- 关键配置受 admin 控制
- 权限最小化

### D. 监控门禁
- 失败告警
- 基础指标
- 业务状态可观察
- 关键动作外部可监控

### E. 验收门禁
- 至少 1 次真实 smoke test
- 至少 1 次真实恢复 drill
- 至少 1 次真实 provider test
- 至少 1 次支付或交易模拟验证

## 7. 建议的执行顺序

1. 先做工程基线：权限、状态、审计、错误码
2. 再做 AI 闭环：provider + task + approval + quota
3. 再做支付闭环：状态机 + webhook + 对账
4. 再做灾备闭环：drill + RPO/RTO + 监控
5. 最后做生产门禁：统一验收

这个顺序可以最大程度减少返工，因为一旦先做具体功能而没做基线，后面修复成本会很高。

---

## 8. 一个简单的判断公式

一个模块是否值得继续开发，取决于：

- 是否对业务关键链路有影响
- 是否涉及资金、库存、权限、数据恢复
- 是否已经有真实调用链和落库动作
- 是否能做 smoke test 和 audit verification

如果答案是“不能”，那么该模块应列入闭环补全，而不是继续扩展。

---

## 9. 最终结论

当前项目最值得优先补的三类闭环：

1. AI / ModaGPT 业务闭环
2. 支付 / 交易闭环
3. 灾备与恢复闭环

这三类是“看起来很像系统”，但其实最容易让工程在生产中出问题的地方，也是最需要先做工程治理的地方。

如果按这个路线推进，项目将从“有很多功能的 demo 平台”升级成“真正可运营的生产平台”。
